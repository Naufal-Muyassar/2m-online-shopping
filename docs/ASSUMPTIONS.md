- P9: Stock model. `stock_snapshots(branch_id, product_id, qty)` stands in for the central stock API; a missing row means 0 sellable (the demo seed gives every product 200). `sellable = snapshot − (ACTIVE + COMMITTED reservations) − branch_products.stock_buffer` (buffer default 0). COMMITTED rows keep counting because the `StockProvider.commit` stub only logs; when a real central API refreshes snapshots, that double counting must be revisited. Redis counters (`stock:{branch}:{product}`, value = sellable, can go negative if a buffer was raised) are the fast path; Postgres rows are the truth. `REDIS_URL` is required in production and defaults to `redis://localhost:6379` elsewhere; Redis runs with `noeviction`.
- P9: Reserve happens in Tx1 after the order and items are inserted: one Lua script checks and decrements all SKUs or none, then `stock_reservations` rows are written in the same tx (expires_at = invoice duration 900 s + 600 s grace, so late payments are still settled by reconciliation). Shortage → 409 `OUT_OF_STOCK` with `details.skus` and `details.items[{sku,name,requested,available}]`; Redis unreachable → 503 `STOCK_UNAVAILABLE` (fails closed). A failed Tx1 gives the counters back unless the reservation rows turn out to exist. Missing counters are seeded lazily from Postgres (`SET NX`); `quote`/`addItem` also reject `out` using the Postgres-derived status, run on the caller's tx connection (a second pool connection deadlocked 50 parallel checkouts).
- P9: Release only touches ACTIVE rows (`UPDATE … WHERE status='ACTIVE'`) and increments Redis only for rows it changed. Triggers: outbox `PAYMENT_EXPIRED`, outbox `STATUS_CHANGED` to CANCELLED/FAILED (so cancelling a PAID order or a failed delivery does not restock; COMMITTED stays committed), the sweeper (every 60 s, rows past `expires_at`), and `PAYMENT_INIT_FAILED` cancellation (released synchronously so the restored cart can be retried at once). `PAYMENT_SUCCESS` marks ACTIVE → COMMITTED and calls `stockProvider.commit("order:{id}:commit", lines)`; if the rows were already RELEASED (sweeper ran before a very late payment) it logs an error for manual review instead of re-reserving. `invoice_id` is filled on the reservation when the order moves to PENDING_PAYMENT.
- P9: The worker rebuilds all counters from Postgres on boot (exclusive advisory lock; every checkout holds the shared one until Tx1 commits). Known gap: if Redis loses a counter while a checkout is between its decrement and COMMIT, the lazily re-seeded value can over-admit by that quantity. Counters that stay low after a crash between the Postgres release and the Redis increment are only repaired by the next worker boot. Existing databases need stock rows (`db:reset:demo`, or insert `stock_snapshots`) or every product shows as out of stock.
